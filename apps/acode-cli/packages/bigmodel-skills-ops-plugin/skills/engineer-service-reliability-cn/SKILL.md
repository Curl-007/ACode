# 服务稳定性与容量规划

可靠性要在业务价值、风险和工程成本之间做可量化的取舍，不是追求无限多个 9。

## 从关键用户旅程定出服务指标

从关键用户旅程定义服务指标（SLI），例如成功率、正确性、延迟或新鲜度。测量点要选能代表用户结果的位置；要不要剔除计划内维护，必须给出明确理由。服务目标（SLO）要写明统计窗口、目标值和统计方法，不能只写一句“高可用”。

SLI 只采集计算用户结果必需的最少数据。租户、用户、请求和业务标识优先聚合或脱敏；密码、令牌、完整身份、支付内容和原始请求，不写进指标标签、可靠性报告和演练记录。要查明细时用受控日志，并遵守组织的留存和访问规则。

历史数据不完整时，先交付候选 SLI、测量缺口和临时目标，不伪造基线。没法在用户入口测量时，写清代理指标会漏掉什么，并安排拨测或抽样对账来校准。

## 算清错误预算和容量余量

用错误预算把发布速度和稳定性挂钩。事先定好预算消耗过快的触发条件、要冻结哪些变更、什么时候恢复，不要等出了事故再临时争论。容量模型从需求、峰值、增长、资源效率和供应周期推导，保留安全余量和降级顺序。

容量至少保留 `日请求 ÷ 86400 × 峰均比 × 增长 × 余量` 的完整测算公式，实例数按单实例安全吞吐来算。用 [容量测算脚本](scripts/estimate_capacity.py) 保证结果带单位、可复算；脚本跑不了就按同一公式手算，单位照样写明。输入缺了就给出参数表和区间，不能拿行业默认值伪造精确实例数。高可用副本、故障域和依赖配额另算，是基础实例数之外的独立约束。

简单错误预算和燃烧率计算优先手算，并在内部交叉复核；只有结构化容量输入比较复杂时，才静默运行脚本。任何计算、脚本或校验状态，不得单独发给用户。内部动作全部做完后只发送一次最终答复，第一句直接给可靠性结论，不出现“计算已验证”“以下是完整方案”这类过程开场。

用户已经给出 SLO、时间窗口和已消耗分钟数时，靠本页方法就够了：不要再读参考文件，不运行脚本，也不发“已获得方法”“让我整理”这类中英文状态句。写出最终正文前保持静默；最终只能有一条用户可见消息。

## 把风险排查落成改进清单

逐项排查单点、依赖、热点、限额、队列堆积、区域故障和人工操作这些风险点。为关键链路设计超时、重试上限、熔断、隔离、幂等、备份恢复和灾难演练。重复劳动按频率、耗时、风险和可自动化程度排序；自动化本身也要有权限、审计和失败兜底。自动化一旦失败，必须能发现、能停下、能转人工，不能默默继续跑。

按服务形态适配：在线 API 看请求结果和尾延迟；异步任务看排队时长、完成的正确性和新鲜度；数据服务看数据完整性和延迟。小团队先覆盖关键旅程，成熟团队再做多窗口错误预算。

交付服务目标、错误预算策略、容量场景、可靠性风险和优先改进清单。每项改进都绑定用户指标和验证日期。监控或容量数据拿不到时，写明哪些项没测到、临时保护边界在哪，不把公开资料当生产证据。方法见[服务可靠性设计](references/method.md)。
