# CI 失败原因定位

## 三十秒开始

直接提供任务对象、当前材料和期望完成状态。可以这样说：

- “这条流水线红了，找第一个因果失败，不要只列最后的报错。”
- “判断这个测试是产品回归还是偶发用例，并给最小复现。”
- “同一提交 Linux 失败、macOS 通过，检查环境差异和责任路由。”

本能力处理的是**一次可定位到提交与运行编号的流水线失败**。先读取现有证据，再产出可复核结果；未读取、未执行或未获授权的事项保持“待确认”“受阻”或“未验证”。

## 输入与缺项处理

优先读取：

- 流水线链接或完整日志
- 提交差异和基线运行
- 执行器、依赖与测试产物

缺少“关键材料”时，先完成不依赖它的结构、风险清单或离线检查，并标明影响。使用以下格式，禁止只说“请提供更多信息”：

> 需要补充以下 N 项才能完成：具体材料、用途、可接受格式。当前已完成：可确认部分。待确认：会改变结论的事项。最小补充项：下一份材料或一次只读验证。

## 执行工作流

1. 先检查最小证据包是否齐全：CI 系统和运行 URL、运行编号、提交 SHA、触发时间、任务矩阵、执行器系统架构、运行时版本、原始命令、完整脱敏日志和测试产物；缺项逐项报告，不用本地结果替代
2. 锁定第一个异常时间点，从后续连锁报错中提取最早因果失败和直接证据
3. 对照相同提交基线、重复运行、依赖锁和执行器环境变化分类归因
4. 在本地或隔离环境构造最小复现，并指定代码修复、测试修复、重跑或平台升级的责任路由与重验条件

执行中保留实际命令、文件位置、版本、时间或截图编号。依赖系统不可用时，离线完成材料审查与复测步骤；失败对应的范围明确写“受阻”，不能用样例结果代替。

## 核心判断

- 下游几十个失败不能掩盖最早的编译或环境错误
- 单次重跑成功只能标记疑似偶发，不能证明没有缺陷
- 日志缺失和任务取消属于证据不足，不应归因给代码

每个判断都要绑定证据位置和核验状态。事实、推断、建议与未验证项分开表达，不能把计划、目标或预计结果写成已经完成。

## 交付物

- 运行与提交身份
- 首个因果失败
- 故障分类与置信度
- 最小复现步骤
- 责任路由与重验条件

完整字段与完成门见 [输出契约](references/output-contract.md)。需要对照真实输入与结果时读 [完整示例](references/examples.md)。

## 安全和禁止行为

- 默认只读流水线与日志
- 不暴露日志中的密钥和内部地址
- 未经授权不取消、重跑、修改检查或合并代码
- 不编造命令结果、系统状态、性能数字、测试通过或外部事实。
- 不执行删除、发布、生产写入、扩大权限或外部发送，除非用户明确授权且目标可核对。

## 能力边界

擅长：围绕一次可定位到提交与运行编号的流水线失败完成证据化分析、方案、审查或验证；能处理材料不全、工具失败和高风险边界。

需要素材：至少需要流水线链接或完整日志、提交差异和基线运行、执行器、依赖与测试产物中的一项；否则只能交付空白框架和最小补充清单。

超出范围：普通代码故障走故障证据定位；发布风险走发布检查；GitHub Actions 专用修复可交给对应连接器工作流。

## 定制参数

可传入技术栈、版本、环境、风险等级、目标受众、输出载体和允许动作。默认按最高风险路径排序；可要求输出飞书文档表格、Markdown、议题草稿或测试清单，但证据和安全门不能关闭。

## 常见问题

1. **只有截图或日志片段能做吗？** 能先提取可见事实；看不到的系统行为保持未验证。
2. **可以直接修改吗？** 只有任务明确包含实现且当前能力范围允许时；否则只给建议或补丁草稿。
3. **工具不可用怎么办？** 保留离线检查、受阻原因和现场复测步骤，不伪造运行结果。
4. **怎么处理敏感数据？** 使用虚构或脱敏样本，令牌、密码、证件号和客户数据不进入报告。
5. **多个问题同时出现怎么办？** 先处理阻断、安全或不可逆风险，再处理质量与体验问题。
6. **输出能直接用于生产吗？** 需由责任人核对版本、环境、审批和完成门；未验证项不能随发布流转。
