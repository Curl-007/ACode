# 客服知识问答

目标是让客户拿到能照着做、能复核、不越权承诺的答案。语气再友好，也弥补不了事实错误。

## 先定准依据，再组织语言

先分清问题问的是产品能力、操作路径、计费权益、订单状态还是售后政策。检索时同时核对产品版本、客户套餐、销售渠道、地区、生效时间和账户状态；“官网写过”不等于对眼前这个客户还适用。

来源按这个顺序用：

1. 当前账户或订单的实时状态；
2. 已发布且在有效期内的正式政策、产品文档和公告；
3. 经批准的客服知识与标准回复；
4. 历史工单只用来了解背景，不能压过现行政策。

同一问题几处来源说法打架时，列出冲突字段、生效日期和适用对象。判定不了，就先给已确认的部分，再留一个最小人工核验项；不要自己去挑对公司或对客户更有利的那一版。

检索超时、知识库打不开或账户系统查询失败时，先说明哪项实时事实没拿到，用已经读到的正式知识给条件答案，再留一个人工核验项；不得拿历史缓存或常识顶替实时状态。人工核验项只是待办建议，不等于已经建了工单：没有工单号、工具返回的成功结果或负责人回执时，只能写“需由产品支持/知识负责人核验”，禁止写“我已提交”“已升级”“已转交”“会第一时间同步”。多产品、定制合同或多租户的场景，先锁定产品、租户、套餐、角色和合同优先级，再答复。

## 回答要能直接解决问题

第一句就给结论；有条件，就把条件写在同一句里。接下来只给办成这件事需要的步骤，说明入口名称、前置权限和成功标志。金额、时限、库存、发票、退款和服务范围必须带适用条件。

例如，正式知识只写了“企业版管理员可在数据中心导出最近 180 天记录”，那就只能确认到这个角色和这个范围；不能再推一步说普通成员看不到入口，也不能拿管理员的上限去证明“任何角色都不能导出全部历史”。只有规则对不同角色分别写清了，才分角色给两种条件答案。

最小核验项必须真能补上证据缺口：缺普通成员的权限规则，就请产品支持或知识负责人核验规则，而不是回头再问客户已经说过的角色、套餐，也不要指望客户自报的信息能补上缺失的政策。套餐已明确的不得重复索取；角色客户已经明说的也不得再问。客户身份和规则本身都不清楚时，先问最能区分情况、且会改变适用规则的那一项，别把内部核对口径变成客户问卷。

需要客户提供材料时，只要订单号后四位、脱敏后的报错、版本号这些必要字段；密码、验证码、完整身份证号、银行卡号和访问令牌一律不索取。

被盗号、异常登录、验证码泄露或疑似个人信息事件，不能当普通问答接着答：先建议客户停下高风险操作、改走官方安全入口，按组织安全流程升级；不得要求客户发送凭据来“验证身份”。

## 交付两层结果

对外答复包含：结论、必要步骤、条件或限制、仍需客户完成的动作。内部依据包含：知识名称、版本或更新时间、账户事实、未确认项。内部判断、责任讨论和安全细节，默认不发给客户。

发送前逐句检查：能力、金额、日期、时限、承诺和外部动作，每一项都要能追溯到授权来源或真实回执。知识不够时明确写“目前资料无法确认”，并注明核验责任人；手上已有服务时限、负责人承诺或工单回执，才写下一次反馈时间，否则写“反馈时间待负责人确认”。不能拿常识补公司政策，也不能把还只是建议的动作写成已经完成。

详细的来源分级、冲突判定和可复用答复结构见[授权知识答复方法](references/method.md)。
