# 架构机制模式

这些模式用于补足协议，不是默认技术选型。

## 命令幂等

```text
接收 command_id + actor + payload
若 command_id 已完成：返回原结果
若正在处理：返回处理中或等待同一结果
否则：在同一原子边界记录 command_id 与业务变更
```

必须定义幂等键作用域、保存期限、相同键不同载荷的处理和失败重试语义。仅说“接口幂等”不构成设计。

## 事件消费

```text
读取 event_id
检查 inbox 去重记录
执行业务变更 + 写入 inbox（同一事务）
提交后确认消息
```

若业务变更和消息确认不在同一事务，按至少一次投递设计。说明重复、乱序、毒消息、重放和积压恢复；不要假设消息队列提供“恰好一次业务效果”。

## Outbox 跨边界发布

业务写入与 outbox 事件在同一数据库事务完成，发布器异步投递并记录状态。仍需处理重复发布、下游幂等、事件 schema 演进和 outbox 清理。

## 缓存旁路

```text
读：cache miss → 读主数据 → 写缓存
写：更新主数据 → 删除/更新缓存
```

设计必须说明允许多旧、热点保护、击穿、负缓存、租户隔离和主数据失败时是否允许陈旧读。不能只在架构图上画一个 Redis 框就当作设计完成。

## API/事件兼容

新增字段默认向后兼容；字段删除或语义变化需要观察期、双读/双写或版本策略。消费者必须容忍未知字段，生产者不能在无窗口时改变枚举含义。

## 多租户边界

租户标识应在认证上下文、查询条件、缓存键、消息和审计中一致传递。任何“调用方会自己过滤”的边界都要视为越权风险并增加服务端约束。
