# 老旧系统升级改造

现代化的目标是降低未来变更成本和业务风险，不是把旧技术全部换成新技术。

仓库探测、脚本和参考资料只在内部使用。用户已经给出变更频率、事故、依赖或迁移边界、且只要方案时，直接拿这些事实写出一条完整答复；禁止先检查默认上传目录、搜索无关工作区，或发送“目录为空”“我将基于事实产出方案”这类过程消息。只有用户明确给出仓库或项目路径、并要求据此分析时，才读取代码。用户没要文件就不创建、不保存，也不宣称已生成迁移计划文件。

## 用变更事实找到热点

运行 `python3 scripts/change_hotspots.py <项目根目录> [近 N 天]`，结合版本历史找出改得频繁、多人经手、单次改动量大的文件。脚本只分析 Git 元数据，不读取远端；结果还要叠加业务关键度、事故、安全、测试覆盖、依赖生命周期和团队熟悉度。代码老但稳定、很少动的区域，可能并不值得先改。

脚本不可用、历史被截断或项目不在 Git 里时，改用发布记录、工单、事故、代码负责人访谈和最近变更清单拼出热点清单，标明这是低置信度结果、证据窗口有多长；不能因为没有版本历史，就按代码新旧排序。

## 先固定行为，再打开迁移接缝

先建立当前行为清单和特征测试，重点保住当前系统里的关键规则、数据和对外接口。看不懂的行为先观测，不在重写中“顺便修正”。涉及适配层、绞杀者模式迁移、双写/影子读或依赖替换时，读取[遗留演进代码模式](references/modernization-patterns.md)，选能独立上线、独立回退的最小切片。

示例用什么语言写，不构成技术栈限制；Java、Go、Python 或其他项目都用同样的端口/适配器边界，并遵循仓库现有的接口和测试惯例。数据库或消息迁移，只在当前切片碰到时才补齐主数据源、兼容期、重放/对账和删除条件。

不要一上来就定微服务、重写语言或新框架。每个切片必须解除一个已证实的约束，能独立交付、验证和回退。双写长期不对账、兼容层永久化、新旧系统各留一套业务规则，这三种局面都要避免。

## 用退出标准结束过渡期

每个阶段都定指标：业务不中断、缺陷率、发布频率、交付周期、恢复时间、依赖风险或运维成本。阶段完成后，删掉旧路径、过渡代码和功能开关。交付现状地图、热点依据、目标边界、迁移切片、风险、验证、回退与退出标准。最终只发送一次答复，第一句就写先处理哪个热点、为什么，不附环境检查、文件生成或方法加载的说明。方法见[遗留系统演进方法](references/method.md)。
