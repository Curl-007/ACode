# 跨团队依赖协调

“等待某团队支持”不是一条可管理的依赖。依赖必须写清交付物、双方负责人、日期、验收方式，以及兑现不了时怎么处理。

## 先拆依赖，不搜索无关环境

每个依赖都记下请求方、提供方、交付物、接口、前置条件、需要日期、承诺日期、验收证据和当前风险。分清它是信息同步、技术接口、资源竞争、审批决策还是供应商交付；这几类的解法各不相同。

用户已经给出团队、等待关系或决策冲突，并且只要方案时，直接按已知事实建依赖卡，不要去搜本机、容器或项目仓库。只有用户要求更新真实项目台账、并提供了文件或系统连接时，才读取相应材料。

把一句含混的“相互等待”拆成一条条能独立兑现的依赖。例如“平台等安全审批、业务等平台接口”必须拆为：

1. 安全团队向平台团队交付审批决定，属于审批决策型依赖。
2. 平台团队向业务团队交付可验收接口，属于技术交付型依赖。

不得把审批日期直接当作接口交付日期，也不得因为审批未定，就替平台编一个开发工期。每张依赖卡至少包含：`编号｜请求方负责人｜提供方负责人｜交付物/接口版本｜前置条件｜需要日｜承诺日｜验收证据｜风险｜合规替代方案｜下一检查点`。值还不知道的，直接标“待确认”，不要编造姓名和日期。

信息不全时，先建一张最小依赖卡，把未知字段标红；追问只问三件事：会改变关键路径的交付物、最晚需要日和双方负责人。项目工具不可用时，就用同样的字段维护一张共享表或带版本的文档，不能退回到群聊里的口头承诺。

## 把口头承诺写进记录

组织双边确认：请求方说清最晚什么时候要、拿不到会有什么影响；提供方确认范围、容量和真正能兑现的日期。口头承诺要写进依赖记录。接口有变化就保留版本和兼容期，不能让群聊里的一句话成为唯一规格。

## 解决冲突，反推最晚决定日

解决冲突，先回到共同目标和事实约束上谈。资源不够，就在范围、顺序、日期或方案上提出取舍；决策权不清，就定一名最终决策人和截止时间。升级卡必须写清“必须决定的问题、可选方案、各自影响、最终决策人、最晚决定日”。

最晚决定日按下游真实需要日反推：`最晚决定日 = 下游里程碑日期 − 决策后技术交付工期 − 集成与验证工期 − 已批准缓冲`。哪个输入还不知道，就保留公式，把“谁在何时补齐该输入”记成下一步行动；给不出具体日期时，直说暂时无法计算，不替团队承诺。替代方案只能是减范围、调整顺序、使用已批准的模拟契约先开发、分期交付或调整里程碑，不得绕过安全审批、权限或发布闸门。

## 维护依赖图，按规模分组

维护依赖图和近期关键依赖，盯住等待时长和对关键路径的影响，而不是把所有关系都收集一遍。最后交付依赖表、接口约定、决策日志、升级项和下一检查点。

核心协调用本页内容就能完成，不依赖 `references/`。只有十个以上团队、需要统一批量卡片格式或画复杂依赖图时，才按已挂载 Skill 的实际目录读取 `references/method.md`；路径确认不了或读取失败，就立即用本页字段继续，不猜文件路径，也不反复重试。最终答复禁止出现 Skill 文件、挂载路径、内部工具尝试或“先读取”这类执行过程。

只有两三个团队时，维护好当前的关键依赖和决策日志就够；十个以上团队时，按工作流分组、指定集成负责人，总图里只放跨组的关键依赖，避免所有团队两两拉会。
