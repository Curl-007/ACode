# 线上故障应急处理

第一目标是减少客户影响，同时保留诊断证据。根因可以稍后确认，破坏性操作不能靠猜。

## 对齐事故现状

确认开始时间、受影响的用户和功能、错误或延迟、数据与安全风险、最近变更和当前趋势。把已观测到的事实、事故假设、进行中的动作和已完成的动作分开记。按客户影响和恢复难度分级，并指定指挥、操作、沟通和记录角色；小团队可以一人兼多角，但不能几个人同时动手却没人记录。

影响范围不明时，先按已证实的最坏用户旅程影响定一个临时等级，同时补齐成功率、地域、租户和数据完整性数据；不要等全量数据到齐才开始响应。监控不可用时，用拨测、客户报告、依赖状态和最近变更交叉判断，并写清观测盲区在哪。

## 可逆止损优先

按见效时间、可逆性和风险来选：回滚、流量隔离、降级、限流、关闭非核心功能或扩容。每个动作写清假设、预期信号、风险、执行人和撤销条件。清库、跳过鉴权、关闭审计、未经验证的大范围重启，这些不得当捷径用。

止损动作失败、执行结果不明或信号恶化时，立即停止重复执行；恢复到动作前状态，并升级到更高一级授权。手里没有安全可逆的动作时，先保住数据和鉴权，公布绕行方案，把卡点说清楚；不能靠试错把事故越搞越大。主沟通渠道失效时切换到预先约定的备用渠道，并且只维护一份权威时间线。

对外更新采用固定更新节奏，只说已确认的影响、当前状态、可用的绕行方案和下次更新时间。证据不足时，不能宣布根因或恢复时间。

时间线、截图、日志摘录、对外通报和复盘，只保留事故判断需要的最少字段；手机号、姓名、订单/账号标识、请求原文和其他个人或商业敏感信息，须脱敏或改用受控关联编号。不得把凭据、令牌或完整客户数据复制进群聊和报告。

## 证明恢复并学习

恢复要由用户关键路径、服务指标和数据完整性共同确认，还要观察满一个稳定窗口；窗口多长，按流量周期、缓存/队列延迟和业务风险来定，不能写死一个通用分钟数。保留时间线、命令、变更、结果和尚未解决的风险。复盘要分析系统和流程两类因素；行动项要有负责人、期限和验证指标，不写“加强注意”这类空话。

每次给出恢复方案，必须显式写出稳定窗口是怎么定的和本次暂定值；例如至少覆盖一个峰值或队列处理周期，并且“关键路径成功、错误/延迟回到阈值、数据对账无新增异常”在整个窗口内持续成立。缺少流量依据时，把窗口标为待指挥确认，不能干脆不写。

## 授权前动作卡

回滚、切流、降级、扩容或重启，请求授权前都要逐项写出：动作、假设、影响范围、预期信号、风险、停止/撤销条件、执行结果确认、用户关键路径、指标阈值、数据完整性检查、稳定观察窗口。窗口未知时写“暂定覆盖一个完整业务/队列周期，具体时长待指挥确认”，不要把这个字段空着。动作卡没填全，就只能继续做只读取证，不能请求执行授权。

事故分级、角色和结束条件见[生产事故响应方法](references/method.md)。
