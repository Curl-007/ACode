# ZCode Configuration Guide

This skill is the **map**: where each extension resource is configured, how scopes combine, and which diagnostic skill to load when something is broken. Volatile facts (command lists, installed skills, configured servers, version) are **not** recited from this file — they arrive in the live snapshot below.

## Read this first: your knowledge of this product is stale by default

This client iterates faster than any model's training data, and even bundled documentation drifts between releases (this guide itself once shipped wrong config paths and a wrong hook-event count). Therefore:

1. **The Current Build section below is ground truth.** It is generated by the running CLI at the moment this skill is invoked. When it conflicts with anything you remember, or with static text in this file, the live section wins.
2. **Bundled references come second.** `references/recent-changes.md` records keys, paths and commands that were renamed or removed. Check it before repeating a name a user may have seen in older answers.
3. **Training data comes last, and never silently.** If you must answer from what you remember instead of the live section or references, say so explicitly and warn that it may be outdated for this build.
4. **A degraded section is a fact, not an absence.** If a subsection is marked `unavailable this time`, tell the user that specific fact could not be collected in this session — never pretend the feature does not exist, and never fill the gap from memory without the declaration in rule 3.

## Two audiences

- **A person** configures through the client UI: Settings → Plugin Management / Skills / Subagents / MCP, and the `/` menu in the input box.
- **An agent** configures by reading and editing the files below with its own file tools. Everything here is written so an agent can find the right file and the right key.

The CLI command in this build is `acode`.

## Scopes, and the files that carry them

**User scope** lives under the home directory and applies everywhere. **Workspace scope** lives inside a repository, applies only there, and can be committed so a team shares it.

| What | User scope | Workspace scope |
|---|---|---|
| Configuration file | `~/.acode/cli/config.json` | `<repo>/.acode/config.json` (or `<repo>/acode.json`) |
| Instruction file | `~/.acode/AGENTS.md` | `<repo>/AGENTS.md` |

The user configuration file carries MCP servers, hooks, plugin enable/disable state, and skill/command disable overrides. The workspace file is searched from the current directory upward to the repository root.

## The resources, side by side

| Resource | Shape | User scope | Workspace scope |
|---|---|---|---|
| **Skills** | directory + `SKILL.md` | `~/.acode/skills/`, `~/.agents/skills/` | `<repo>/.acode/skills/`, `<repo>/.agents/skills/` (every directory from cwd up to the repo root) |
| **Commands** | a `.md` file | `~/.acode/commands/`, `~/.agents/commands/` | `<repo>/.acode/commands/`, `<repo>/.agents/commands/` |
| **Agents** | a `.md` profile | `~/.acode/cli/agents/` | `<repo>/.acode/agents/` |
| **MCP** | a JSON object | `~/.acode/cli/config.json` → `mcp.servers` | `<repo>/.acode/config.json` → `mcp.servers`; `<repo>/.agents/mcp.json` → top-level `mcpServers` is a lowest-priority compatibility fallback |
| **Hooks** | config object | `~/.acode/cli/config.json` → `hooks` | `<repo>/.acode/config.json` → `hooks` |
| **Plugins** | directory + `.acode-plugin/plugin.json` | installed from a marketplace; state lives in `~/.acode/cli/config.json` | — |
| **Instructions** | an `AGENTS.md` file | `~/.acode/AGENTS.md` | `<repo>/AGENTS.md` (the `/init` flow also treats `<repo>/.acode/AGENTS.md` and `<repo>/.agents/AGENTS.md` as candidate locations) |

A plugin contributes skills, commands, hooks, MCP servers and agents from its own roots; `.claude-plugin/`, `.codex-plugin/` and `.cursor-plugin/` are accepted as compatibility manifest names.

## How scopes combine

Configuration layers merge in a fixed priority order — each layer overwrites the same-named entries of the layers below it:

`system < user < project(workspace) < session < env < CLI flags < managed policy`

Two consequences worth stating in answers:

- For a same-named MCP server, the **workspace layer overwrites the user layer** in this build. (Older answers claimed the opposite; see `references/recent-changes.md`.)
- The managed **policy** layer sits on top but can only **tighten** (deny rules, disallowed tools) — a repository can never widen permissions through its config file. Within the project layer, `permission.disallowedTools` merges as a union with the user's, so a repo cannot silently clear a user's hard-disabled tools.

## Discovery order for skills and commands

Both scan the same locations, earliest first: explicitly configured roots → user `~/.acode/…` → user `~/.agents/…` → workspace `.acode/…` (cwd up to repo root, deeper wins) → workspace `.agents/…` → enabled plugin and bundled roots last.

- **Skills** are identified by file path; when several same-named skills are discovered, the first match in discovery order is the one that loads — the rest are shadowed.
- **Commands** are keyed by normalized name, first match wins. Nested directories join with a colon: `review/code.md` becomes `/review:code`.

## Hooks: always say which surface you mean

Two different event surfaces exist, and conflating them produces wrong answers:

- The **config-file** surface (`hooks.events.*`, strict schema) accepts a small fixed set of event keys and is gated by `hooks.enabled`.
- The **runtime** event vocabulary (contracts layer) is larger and evolves.

Do not recite either list from memory. Point at the config schema or the Current Build snapshot, and load `diagnosing-hooks` for anything not firing.

## AGENTS.md merge behavior

The user instruction file is injected first and the workspace file second; later text wins on contradictions, which is how a repository narrows a broad personal default. The built-in `/init` command targets the **workspace** file. Onboarding may offer to migrate `~/.claude/CLAUDE.md` into `~/.acode/AGENTS.md`.

## Picking a location

- Personal and cross-project → user scope (`~/.acode/…`, or `~/.agents/…` to share with other tools).
- Shared with a team, versioned with the repo → workspace scope.
- Shadow a same-named `~/.agents/` skill inside this client only → `.acode/skills/`.
- MCP servers → user config for personal ones, workspace config to share; since a workspace declares servers that connect when the project is opened, only open repositories you trust.
- Secrets → never commit them; use environment variables or local settings, and never echo config values into answers.

## Answer style discipline

- **Pasteable JSON only.** Config examples you give must be valid JSON: no comments, no trailing commas, no `...` placeholders. If a fragment must be partial, say so in prose around it.
- **Name the landing spot.** Every setting you recommend must state the file it lands in (`~/.acode/cli/config.json` vs `<repo>/.acode/config.json`) and the exact key path (`mcp.servers.<name>`, `hooks.enabled`, …).
- **Never invent names.** Key names, command names and event names come from the live section, the config schema, or references — not from pattern-matching on other products' configs.
- **Migrate stale names.** If a user quotes a path or key from `references/recent-changes.md`, answer in terms of the current name and say what changed.

## Routing: which diagnostic skill to load

When a configuration is read but has no effect, or reports an error, load the matching skill; each runs a symptom → cause → check → fix workflow covering both the UI action and the file-and-key edit:

- MCP server will not connect, tools missing, untrusted, or timing out → **`diagnosing-mcp`**
- Skill not discovered, not triggering, shadowed, or disabled → **`diagnosing-skills`**
- `/command` missing, overridden, bad frontmatter, or arguments not substituting → **`diagnosing-commands`**
- Hook not triggering, matcher not matching, script not executable, or blocking unexpectedly → **`diagnosing-hooks`**
- Plugin not listed, install failing, components missing, or not enabled → **`diagnosing-plugins`**
