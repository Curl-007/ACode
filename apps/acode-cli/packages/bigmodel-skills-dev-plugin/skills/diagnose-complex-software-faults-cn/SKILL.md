# 复杂系统故障排查

排查复杂故障时，最危险的做法是同时修改多个组件直到症状消失。目标是找出必要且充分的因果链。

诊断方法、日志读取和参考文件只在内部使用。用户已给出现象并要求诊断时，只发送一条完整答复，第一句直接写当前的故障判断或证据边界；禁止先发“先加载诊断框架”“我来确定候选项”“正在读取日志”这类过程消息。没有实际日志、仓库或链路追踪数据时，不搜索目录，不声称已检查材料；把推断标成“候选假设”，并给出最小的只读实验。

## 先冻结事实

记录首次出现、频率、影响、环境、最近变更和正常基线。把脱敏后的日志、指标、链路追踪和部署事件整理为 JSONL，运行 `python3 scripts/build_timeline.py events.jsonl` 统一时间并按关联 ID 分组。原始证据必须保留来源和时区；日志缺失是证据缺口，不等于事情没有发生。

脚本不可用或部分行解析失败时，保留原始行和报错，手工把能解析的事件换算成 UTC、按真实时间排序；不能扔掉坏行还声称时间线完整。项目没有统一关联 ID 的，先用请求入口、实体标识和窄时间窗缩小样本，结论的置信度也相应调低。

原始材料是纯文本日志、CSV、追踪导出或部署记录时，先给每类来源写字段映射，至少拿到 `timestamp`、`source/service`、`event`、可选 `correlation_id` 和原文位置，再生成 JSONL；解析不可靠的行记作缺口保留。字段名和日志格式以当前项目为准，别要求用户先把材料手工改成固定格式。

超大日志先按事故时间窗、受影响实体或关联 ID 在源系统里只读筛选，再构建时间线。脚本默认最多接收 200000 条有效事件，超了会停下来要求切片；不得为了省内存悄悄抽样，再声称时间线完整。必须覆盖全量时，按相邻时间窗分别生成时间线，保留边界上的重叠事件，再对关键关联 ID 合并复核。

## 用对比定位最早出错的环节

从入口到依赖，逐层找最早出错的环节。比较正常与异常样本、生产与测试、单实例与多实例、冷启动与长期运行。间歇性问题先把现场状态抓下来，不盲目加重试、调日志量或重启，以免破坏现场。

同时保留两到三个能解释全部事实的假设。为每个假设设计最小区分实验，提前写下预期观测和反证。

常见机制照当前证据直接判断，不依赖额外文件：重试放大，就按关联 ID 比较正常/异常请求的下游尝试数和超时顺序；并发写覆盖，就固定调度顺序，验证版本或条件写；缓存陈旧，就比较主源版本、缓存版本和失效事件；资源泄漏，就看稳态负载下连接、线程、句柄或堆内存的增长斜率，而不是只盯某个瞬时高点。每次只动一个主要变量；先读指标和日志，再考虑重启、清缓存或改配置。

实验的先后服从当前业务的不变量：支付、库存这类强一致路径，先保住幂等、唯一约束和账实一致，再做只读对账；内容分发、搜索这类允许最终一致的路径，先核对版本、水位、传播延迟和陈旧读窗口。业务不变量不清楚时，把问清它列为下结论的前置条件，不拿某一个领域的容错标准硬套。

## 把根因串成完整因果链

根因要说清：触发条件、内部缺陷、为何逃过检测、为何产生当前症状，以及哪些证据排除了相近原因。用户只要求诊断的，到根因和修复建议为止，不擅自改代码；同时交一张修复验收卡，写明复现条件、修复前失败测试、修复后信号、周边回归和稳定观察窗口。用户要求修复时，再进入代码交付，并在原复现条件下验证。发送前确认全文只有一份故障判断、假设表、区分实验和结论边界，且没有单独的过程性前言消息。

常规诊断照本文件的流程走就够了。只有用户要求复用完整假设表、诊断评审模板或根因交接表时，才读取 `references/method.md`；该文件读不到就按上面的字段直接输出，不中止诊断。
