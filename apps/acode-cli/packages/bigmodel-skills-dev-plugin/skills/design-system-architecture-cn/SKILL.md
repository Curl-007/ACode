# 软件系统架构设计

从质量属性和失败模式出发设计，而不是先选微服务、消息队列或某个云产品。

## 交付闸门

计算、脚本复核、资料读取和方案比较都在内部完成。不得发送“先检查脚本”“现在运行估算器”“让我查看参考资料”等过程消息，也不得把内部操作写进最终答复；内部工作全部做完后只发一次最终答复，第一句直接给架构判断或容量结论。工具或脚本失败时直接改成手算，并用等价公式复核；失败过程不发给用户，工具报错也不写进答复。用户未提供仓库、附件或系统材料时，不搜索默认目录或平台自身文件；先拿用户给出的事实把能做的部分做完，再点明真正影响结论的最少几项缺口。用户未明确要求交付文件时，不创建临时输入文件，不宣称已保存、生成或可下载任何文件。

## 把业务约束变成可验证数字

明确核心用例、数据一致性、峰值流量、延迟、可用性、恢复目标、合规、成本和团队能力。常规容量估算直接手算并用等价公式复核，不为调用工具额外创建输入文件。只有用户已提供可用 JSON 文件、明确要求用脚本复算，或参数多到手算易错时，才静默运行 `python3 scripts/capacity_estimator.py assumptions.json`；调用前先确认路径真实可用。脚本只做算术，不替业务补数字；没有依据的输入，给出范围并标成待测指标。

用户已经给齐某项估算的输入时，必须在本次答复中直接写出公式、代入值、结果，以及架构还缺哪些约束；不得只说“先建立假设”“运行脚本”，也不得要求用户自己执行。脚本用于复核回答，不替代回答。脚本跑不起来就立即手算，能算的部分照常交付。

脚本不可用时，保留输入、单位和公式，手工估算并做数量级复核；关键输入缺了，就给范围或标成待测指标，方案不能卡在这里，精确数字也不能编。法规和行业管控，只在用户场景确实涉及、且有权威依据时才纳入约束；不因为是“中国项目”就自动套一份合规清单。

容量结果必须展开单位，并用另一条等价路径复核。例如存储同时按“每日请求 × 单条字节 × 天数 × 余量”和“每用户每日字节 × 用户数 × 天数 × 余量”计算；字节转 GiB 时明确除以 `1024³`，转 GB 时明确除以 `1000³`，不能漏掉十倍或千倍量级。用户只给一个“容量余量”且没有限定用途时，默认对计算、存储、带宽三类设计容量同时生效，并在表头写明；若余量只用于其中一项，必须明说是哪一项，不能在不同资源之间悄悄用不同口径。

实例数先计算裸峰值所需实例 `ceil(峰值 RPS ÷ 单实例安全 RPS)`，再计算含容量余量的设计实例 `ceil(峰值 RPS × 容量余量 ÷ 单实例安全 RPS)`；最终规模采用后者。故障域、N+1 和可用区副本是容量余量之外的独立约束，不能把二者混为一个数字。存储表必须同时列出“原始保留量”和“含余量设计量”；本地缓存、索引、日志、副本和备份等项若没算进去，要逐项标出来，不能藏在余量里。

发送前把摘要、容量表、独立验算和结论里的每个数字逐项对账；哪一处和公式结果对不上，就重算，并把这个数字出现的所有位置都换成新值。两条路径对不上、或摘要和表格对不上，先修算术再谈架构选择，互相矛盾的数字一个也不能留。

## 设计边界和失败语义

按当前的业务语言、变更频率、数据所有权和事务边界切分模块，不要拿技术分层的名称反推服务。同步调用、异步事件、缓存和副本，都要讲清超时、重试、幂等、顺序、重复、部分失败，以及恢复责任归谁。

涉及 API、事件、缓存、跨服务一致性或多租户时，读取[架构机制模式](references/architecture-patterns.md)。里面的代码和伪代码只用来查协议缺口，落地时必须换成当前系统的真实命令、事件、实体和约束。

敏感数据从采集、传输、存储、访问、审计到删除，每个环节都要有管控措施。密钥不出现在架构图、示例和日志里；需要真实拓扑或配置时先脱敏。

## 用备选方案把取舍摆到明面上

至少保留一个更简单的备选方案，在复杂度、交付速度、扩展、可用性、成本和可观测性之间写清取舍。团队部署不了、调试不了、恢复不了的架构不算可行。不要拿“行业最佳实践”代替当前约束下的选择理由。

对关键路径做容量和故障演练：单点、依赖超时、消息堆积、热点、部分写入、跨区故障和回滚。交付业务上下文、组件/数据图、关键时序、容量公式、部署、观测、安全、风险和演进阶段；关键选型写 ADR（架构决策记录），并说明何时重审。方法见[系统架构决策方法](references/method.md)。
