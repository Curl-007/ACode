# 项目延期诊断与恢复

健康报告要把兑现不了的承诺摆出来，帮团队做取舍；不能为了面上稳定，把红灯报成黄灯。

## 重建真实状态

衡量进展看已验收产物而非任务完成百分比。把基线和当前预测放在一起比，逐项检查关键路径、范围变化、缺陷与返工、资源到位情况、依赖、待决策事项和收益假设。事实、预测和团队判断要分开记。

没有可信基线、项目系统也用不了时，就从最近已验收的产物、硬期限、进行中的工作、关键依赖和实际能到岗的人员，重建一版“最小事实基线”。互相冲突的数据并排列出，标明来源和更新时间；空字段不能当绿灯。

Skill、参考资料或项目系统不可用时，直接用本页方法和用户已给的事实，不搜索路径，也不解释框架加载。只发一次最终答复，第一句直接给健康判断；禁止“这是典型场景”“让我先加载”“已读取方法”这类过程消息。

先分清偏差是偶发事件，还是系统性问题。里程碑接连延期、完成标准不断放宽、关键人员被多个项目超额占用、风险挂了很久却没有触发条件，都是项目陷入停滞的信号。

## 设计恢复而不是催进度

先保住必须实现的业务结果和不可逆节点，再列出几条路：减范围、增资源、调整顺序、改变方案、分阶段交付，或者停止项目。每条路都写清收益、成本、风险和对新日期的影响。不能把加班当成默认的恢复方案。

定了方案，就重建范围、关键路径、负责人、决策点和验收基线。设置两周左右可观察的先行指标，比如关键接口冻结、首个端到端切片通过，而不是只盯最终日期。

## 管理重新承诺

把需要管理层拍板的范围、预算、资源和日期，汇总成一份明确的决策请求。按固定频率复核恢复指标；一旦触发失败条件，就上报、换方案或停止，不再悄悄延期。

最后交付健康诊断、根因、恢复选项、新基线、触发条件和决策请求。记录模板见[项目健康与恢复方法](references/method.md)。
