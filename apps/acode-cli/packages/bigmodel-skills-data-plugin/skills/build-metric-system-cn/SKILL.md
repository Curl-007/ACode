# 业务指标体系设计

指标体系是一套共同的决策语言，不是从行业清单里挑十个 KPI。搭完之后，业务、产品和数据团队再问“成功是什么、哪里出问题、谁维护定义”，答案应该只有一个。

## 选择核心价值指标

从一项反复发生的用户价值入手：谁完成了什么有价值的结果，频率或规模在怎么涨，它为什么能预示长期业务结果。累计注册、总浏览量这类只涨不跌的数字，通常不能当核心指标。

业务模式还看不清时，先拿“用户是谁、获得什么价值、多久发生一次、团队能影响什么、不能牺牲什么”这五问搭一条暂定的价值路径，没确认的点明确标出来。先交付一棵最小树：一个核心结果、三到五个关键驱动，加上必要的护栏；只有决策确实需要时再扩，不要让指标树膨胀成看板目录。

候选指标要过四项检验：和用户价值同向、团队能影响、不会轻易被刷高、能稳定采集。业务里同时有交易与订阅、内容与交易这类多条价值路径时，一条条分开写清楚，再按当前战略阶段选出主路径，不强行压成一个万能指标。

## 构建指标树

以核心指标为根，只保留三种节点：

- 结果指标说明最终表现；
- 驱动指标解释团队可以影响的前置环节；
- 护栏指标防止增长以体验、质量、利润、成本或合规为代价。

父子节点的关系必须解释得通，最好能用加法、乘法或明确的业务机制连起来。指导不了行动、取数不稳定，或和其他节点重复的指标，从主树里移除。常见业务的拆解提示见[指标树模式](references/metric-tree-patterns.md)，只能按价值路径选用，不能整表照抄。

## 定义口径和归属

进入主树的每项指标，都要有一份能落地的定义：业务含义、公式、分子分母、统计对象、事件或状态、去重身份、时间窗口和时区、纳入与排除、数据源、更新延迟、下钻维度、负责人和生效版本。跨团队治理还要消除同名异义或同义异名，保留唯一标准名称和别名映射。

这些字段没有一项是可选的。交付正式口径卡时，按[指标树模式](references/metric-tree-patterns.md)里的口径卡逐项写；还没确认的字段标为“待确认”，不能直接省略。时间口径至少写清自然日还是滚动窗口、时区和跨日归属，免得同一事件在不同系统里落到不同日期。参考文件或指标平台不可用时，用 Markdown 表把同样的字段留全，不省略治理信息。

同名异义、同义异名都要明确解决。多个历史口径并存时，定一个正式名称和主口径，旧口径的版本、影响范围和迁移日期都留档，不能回写历史让趋势看起来连续。

## 建立治理机制

每个指标都要有业务负责人和数据负责人。新增、修改、停用必须记下提出原因、影响的看板和目标、对历史数据的处理、批准人和生效时间。正式指标发布前，先用正常、边界和排除样例走查，再用真实数据抽样复算、对账。

口径迁移时，列出受影响的看板、报表、目标、接口和下游任务，把旧版停算、新旧双跑、差异核对、新版生效、旧版下线的顺序排清楚。历史数据默认保留原口径并标注版本；要提供按新口径重算的历史序列，就单独存成一个视图，不能为了曲线连续悄悄覆盖旧值。

最终交付的是核心指标说明、最小指标树、逐项口径卡和变更规则。这项工作可以单独做，不要求先把数据清洗好，也不负责解释某个月为什么跌了；一次性的经营诊断交给“经营差异分析”，产品使用和留存分析交给“用户行为与产品分析”。
