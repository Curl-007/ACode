# 项目计划与排期

项目计划要从可验收成果倒推，而不是从会议日期和任务数量开始。

## 把假设和承诺分开记

先弄清业务目标、不做什么、成功标准、硬期限、预算和外部约束，再找出关键干系人、决策人、验收人和执行负责人。假设和承诺分开记：没有负责人确认的日期，只能算计划假设。

信息不全时，先交付一版最小计划骨架：已知成果、暂定不做的部分、最关键的三个待决策事项，以及近期要做的摸底调研；范围还没明确的部分，不排精确日期。法定节假日、采购、审批、安全评审、供应商和上线窗口，只在项目确实涉及、日历也已确认时才排进计划。

## 从依赖图推出关键路径

把成果拆成工作包，一个包一个责任人，做没做完可以验证。识别技术、资源、审批、采购、法务、供应商和上线这些依赖，算出关键路径和浮动时间。工期要写清估算依据和区间，并给集成、返工和验收留出时间。

关键路径必须从依赖图和工期推出来。可以用 [关键路径脚本](scripts/critical_path.py) 读工作包 JSON 来算；项目系统用不了，就用同样的字段维护一张本地表，不能因为工具不可用就省掉依赖。敏捷项目按可验收切片规划，固定范围项目按阶段门规划，两种做法都要保留端到端验收和变更影响分析。

用户没给结构化的工作包 JSON 时，就用题目里的范围、团队和期限，先给一版可执行的假设计划，不为了运行脚本自行搜索或创建输入文件。需要算关键路径时，静默手算或静默跑脚本；读取、计算和校验的过程一律不得向用户播报。完成后只发送一次最终答复，第一句直接给项目判断，不出现“我已掌握技能”“让我构建”“计算完成”“我先完成文档”这类过程文字。

## 拿证据验收，不粉饰进展

每个里程碑都写上产物、进入条件、完成证据、负责人和验收人。建好范围、时间、成本、质量和风险基线；变更请求要写清对关键路径、资源、预算和收益的影响，由有相应权限的决策人批准。

盯住三种假进展：任务完成了一大堆，却没有可验收的切片；里程碑只有日期，拿不出证据；隐藏依赖没有双方承诺。发现了就回到成果、接口和验收本身，不靠拉高完成百分比来粉饰计划。

最后交付项目章程、工作分解、关键路径、里程碑、资源、风险、近期行动和基线假设。规划检查项与字段模板见[项目交付规划方法](references/method.md)。
