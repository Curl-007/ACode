# 监控、日志与告警设计

衡量可观测性，不看采集了多少数据，看值班人员能不能快速回答“谁受影响、哪里开始偏差、为什么”。

## 从问题而不是工具出发

列出关键用户旅程、服务边界、依赖，以及必须回答的故障问题。在入口生成关联 ID 并全链路透传，统一服务、环境、版本、租户这些低基数维度；禁止把用户 ID、订单号这类高基数或敏感信息不加管控地写进指标标签。

指标看趋势和目标，日志留离散事件和上下文，链路追踪展示跨组件的因果。每类遥测数据都写明产生位置、字段、采样、保留期、脱敏、成本和负责人。日志要结构化，但不能记密码、令牌、完整身份或支付数据。

按服务形态区分信号：在线请求看成功、正确性和尾延迟；队列和批处理看排队时长、吞吐、重试和最终是否完成；流处理看事件时间延迟和检查点；数据产品看完整性和新鲜度。不能拿同一张“黄金信号”表套所有服务。

服务形态没说明时，先用入口—处理—依赖—结果四段建一个通用最小字典，把队列、流处理和数据新鲜度列为待确认分支；不要因为信息不足就停住，也不要默认用某个云厂商或观测产品。项目若受数据驻留、跨境、等保或供应商托管约束，先拿到组织实际的定级、数据分类分级、保留和访问控制要求，再纳入设计；没拿到正式要求就标为待确认，不能自行编造等级和脱敏映射。

## 让告警可以行动

每条告警都要对应用户影响、错误预算消耗或明确的容量风险，并包含严重等级、阈值依据、持续时间、去重、负责人、看板和操作手册。静态资源阈值不能替代用户结果；收到后没有动作可做的告警，应删除、降级或转成看板。

会通知到人的告警，负责人、关联看板和操作手册一个都不得省；三者缺任何一个，就只能算待完善规则，不能标为可上线告警。输出告警目录时逐行保留这三个字段，不能因为正文提过就省掉。

有 SLO 时，优先用多窗口错误预算燃烧率来告警，把短窗口的快速事故和长窗口的慢性退化分开。没有稳定基线时，先静默观测、标注事件，再定阈值，不能随手写个百分比当通用标准。

看板按“影响 → 入口 → 依赖 → 资源 → 变更”组织。用已知故障或演练来验证：有没有触发、有没有定位到正确的层、上下文够不够、有没有产生噪声。

观测系统自己也会坏。基数爆炸、日志洪峰、采样漏掉错误链路、采集器积压、后端不可用，这些都要设成本和健康信号；保留独立健康检查、关键变更记录和受控本地日志，作为降级入口。遥测缺了就明说“不可观测”，不得把没有告警当成服务健康。
