# 复杂故障实验模式

## 重试放大

症状：上游少量超时后，下游 QPS、连接数和延迟同时上升。

区分实验：按关联 ID 统计一次用户请求产生的下游尝试数；对照无故障样本。若关闭某一层重试只在隔离环境进行，并预先写明预期的尝试数和错误率变化。修复通常需要总超时预算、指数退避、抖动、最大次数和幂等，不是再加一层重试。

## 缓存一致性

比较同一业务键在主数据、缓存与返回值中的版本/更新时间。用“绕过缓存的只读请求”区分源数据错误与缓存陈旧；不要在取证前全量清缓存破坏现场。

## 并发丢失更新

```text
两个请求读取 version=7
A 写入并更新到 version=8
B 仍按旧值覆盖
```

用屏障控制两个线程在读取后同时继续，使问题稳定复现。若加入 `WHERE version = 7` 后一个请求得到明确冲突而数据不再丢失，支持该假设。

## 连接/监听器泄漏

固定请求模型和时间窗，比较创建数、释放数、存活数和堆/连接池曲线。停止流量后仍不下降支持泄漏假设；仅看到内存升高不足以证明泄漏，可能是缓存或 GC 周期。

## 环境差异

生成配置指纹，只比较非敏感结构：版本、开关名与布尔值、依赖端点类别、区域、时区、字符集。严禁把密钥、token 或完整连接串放入报告。一次只对齐一个差异并观察结果。

## 时钟与顺序

跨服务时间线先保留原时间和时区，再统一为 UTC；检查时钟漂移、采样和日志缓冲。日志显示顺序不一定等于业务提交顺序，优先使用事务版本、序列号或追踪关系。
