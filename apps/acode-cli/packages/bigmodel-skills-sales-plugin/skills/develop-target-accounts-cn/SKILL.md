# 目标客户筛选与触达

目标不是名单越长越好，而是每个客户都能说清“为什么匹配、为什么现在、为什么值得联系”。

## 建立可验证的客户画像

画像从已成交和流失的客户、产品价值、交付边界推出来，落到行业、规模、地域、业务模式、技术或合规条件、痛点和排除项上。每一条都要可观察，“重视数字化”这类没法验证的形容词不能用。

查工商与官网、招聘、公告、招投标、融资、产品变化、管理层变动、技术栈和公开内容。企业、联系人、职位、联系方式和信号，每一项都记下来源和日期；不采集非必要的个人敏感信息，来源不明的数据不买也不用。

用户只让核验一家企业的一个当前产品信号时，按输入在两条路径里选一条，不在同一轮里既搜索又读取：

- 已知官网 URL：只读取该 URL。读到官方原文后输出“已核验信号”；读不到原文就明说失败，不改用搜索补答案。
- 未知官网 URL：只搜索官方候选入口。输出“候选来源，尚未完成原文核验”，不得继续读取网页，也不得把搜索摘要当产品事实。

每条路径拿到一个来源、够回答当前这一步的问题就停，不把单信号任务扩成整家公司的研究。访问或搜索日期写本次运行环境的当前日期，不能拿网页发布日期或搜索结果里的年份去推。

网页搜索、原文读取和证据比较都在内部做完，不向用户播报“开始搜索、结果已返回、现在读取、网页读取成功、已成功读取、停止扩搜”这类工具状态，也不出现“本次工具读取”“工具读取确认”、web reader、web search、MCP、Skill 或工具名称。工具调用结束后只写一次客户答复，第一句只用“触达判断：足以……”或“触达判断：不足以……”，后面紧跟业务理由，不写取证动作。随后给出来源状态、URL、发生/访问或搜索日期、证据强弱和不可外推项；来源状态直接写“官网原文”或“候选来源”，内部怎么取到的不解释。后续核验建议只写需要核验的原始来源，不写用了哪个内部工具。用户明确不要联网时不调用网页工具，只用用户提供的材料，并标明证据边界。

数据源不可用时，把待核验的企业和还缺的来源记下来，不拿模型记忆去补联系人或购买信号。任何失败返回都只代表“原文内容未取得”，不得引用、翻译、概括或解释失败返回本身。失败答复固定写成“触达判断：不足以支持触达。当前未取得〔来源 URL〕的可读原文，无法确认产品信号；在原文恢复可访问前不外推产品、时间或客户需求。”随后最多补来源 URL、访问日期和重试条件；不得出现工具名称、“工具”“调用”“读取失败”、服务名称、HTTP 状态、余额、资源包、错误码或内部过程。发送前草稿里若有这些词，删掉失败解释，改成上面那句固定业务口径。公开联系方式也要记下来源、访问范围和停止联系状态；名单不得进入无权限的个人表格或聊天记录。

## 用信号决定优先级

匹配度回答适不适合，信号强度回答为什么是现在，可触达性回答能不能进入有效对话。三项分开打分。负面信号包括：产品服务不了、采购冻结、对方已有排他合作、有明显合规风险。

每项使用 0～3 级可观察锚点并保留证据：0=不满足或反向，1=弱推断，2=有一项近期正式信号，3=多项独立近期信号。工商身份和联系人角色过了复核周期、招聘停了或招标结束了就降级，过期信号不能一直挂在高优先级上。

每个客户选一个最强的业务假设和一个可验证的问题。个性化内容要引用真实信号，但不能装作认识对方，也不能让内容看起来像在监控对方。触达先讲对方的情境和可能的价值，再给一个门槛低的下一步；同一段模板不要群发。

## 设计合规触达节奏

按国内渠道规范和用户偏好安排邮件、电话、企业微信或公开社媒。设置频率上限、退订或停止联系、工作时间和去重规则。未经批准不自动发送。

交付客户名单、证据、评分、关键人、触达文案、节奏和验证指标。没回复不等于没需求；先检查渠道、角色、假设和时机，再决定降不降级。证据卡与纠偏规则见[目标客户开发方法](references/method.md)。
