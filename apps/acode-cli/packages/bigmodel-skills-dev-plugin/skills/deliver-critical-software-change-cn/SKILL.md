# 关键功能开发与交付

完成不是“代码已经写完”，而是目标行为可验证、变更风险受控，并且出了问题能恢复。

## 读取仓库既有的交付约定

运行 `python3 scripts/inspect_project.py <项目根目录>`，定位语言、构建系统、测试、迁移、容器与 CI 配置；再读仓库说明、相邻实现和近期相关变更。脚本不会安装依赖，也不会猜运行命令。复述当前行为与期望行为，把验收标准写成可观察的结果，覆盖正常、边界、权限、失败和兼容。凡是会改到数据或对外行为的地方，有歧义必须先问清楚。

目标环境没有 Python 3 或脚本不可用时，直接手工检查仓库说明、构建清单、测试目录、迁移和 CI 配置；脚本只是只读加速器，不是交付的前置条件。只运行项目文件里写明的命令。扫描或测试受阻时，交付已确认的范围和补采清单，不把工具失败写成代码通过。

没有提供仓库但任务已描述目标行为时，先给“待落库变更包”：预期修改层、接口/数据兼容顺序、修复前失败测试、发布与回滚闸门；类名、表名、命令这类要等拿到仓库才能定的占位项，逐项标出来，不得声称代码已经交付。拿到仓库后，必须把占位项落到真实文件上并跑完验证，方案稿不能当最终交付。

内网 Git/Gitee、私有 Maven/npm/镜像仓库、受限 CI 这些国内团队常见的设施，一律按当前组织的配置来用。依赖被网络或权限卡住下不来时，记下失败命令、缺哪个仓库或权限、以及在授权环境里怎么复跑；不擅自切到来路不明的公共镜像，也不把依赖不可达误判成业务测试失败。

## 先建立失败证据再改

先建立能稳定失败的测试或复现证据。修改集中在拥有该行为的层，不要在别的层塞回退值来掩盖契约错误。复用项目惯例，别把一次变更扩大成无关的重写。

涉及接口兼容、数据库变更、幂等、并发、异步处理或功能开关时，读取[关键变更代码模式](references/change-patterns.md)，只挑当前任务用得上的模式。示例给的是关键控制项，不是预制业务模型；实体、事务边界和错误语义必须来自当前仓库。

## 把代码、迁移和发布当作一个变更

接口或数据变更采用兼容窗口，说清新旧读写、回填、校验和清理的顺序。每个功能开关都要写明负责人、默认值、观测指标、退出条件和删除日期。回滚不能依赖尚未验证的备份；不可逆迁移应使用前滚修复或兼容读路径。

审查安全、正确性、并发、性能、可维护性和可观测性。测试、类型检查、静态检查和构建，只跑脚本找到且仓库文件里确认过的命令，跑完再用原需求路径验证一遍。交付变更摘要、测试证据、迁移、发布/回滚和剩余风险。闸门清单见[关键软件变更检查](references/method.md)。

外部输入、日志和迁移样本遵循仓库既有的脱敏规则；令牌、连接串和非必要个人信息，不能进补丁、测试夹具或交付报告。法规专项只在本次变更确实涉及相应数据或系统边界时才触发。
